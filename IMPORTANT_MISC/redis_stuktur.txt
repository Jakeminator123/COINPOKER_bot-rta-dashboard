Redis-struktur för Bot & RTA Detection System
===============================================

Detta dokument beskriver den faktiska Redis-struktur som används i projektet.
Både Python-scannern (core/redis_schema.py) och Next.js-dashboarden (lib/redis/schema.ts)
använder samma schema helpers för att säkerställa konsistens.

Dashboardöversikt
-----------------
Efter inloggning på Bot & RTA‑Detection visas en översikt över alla spelare. Navigeringen består av tre flikar:
•	Overview – visar sammanfattande statistik, t.ex. antal online‑spelare, totala unika spelare, andel hög risk och genomsnittlig hotnivå. I listan under dessa rutor kan man söka och sortera spelare. Varje spelare visas som en kort ruta med namn, hotnivå, antal detektioner och kritiska incidenter.
•	Device Manager – klickar man på en spelare hamnar man på en detaljsida med namn, enhets‑ID, status, sista aktivitet och aktuell risk. Sidan innehåller också riskanalys, hotmätare (bot‑probabilitet), live feed för detektioner, historiska analyser och kategorier (program, nätverk, beteende, virtual machines, script & automation). Där finns även snabbknappar som "Emergency Mode", "Kill CoinPoker Client" och "Take Table Snapshot".
•	Settings – inställningsflik (ej detaljerad här).

Denna struktur är optimerad för realtidsöversikt och enskild analys.

Faktisk Redis-struktur (implementerad)
=======================================

1. Device Hash (`device:{device_id}`)
--------------------------------------
Varje spelare/enhet lagras som en Redis hash med följande fält:

Key: `device:{device_id}` (t.ex. `device:462a6a3a5c173a1ea54e05b355ea1790`)

Fält i hashen:
  device_id => "462a6a3a5c173a1ea54e05b355ea1790"
  device_name => "DESKTOP-XYZ" (hostname eller datornamn)
  device_hostname => "DESKTOP-XYZ" (kan vara samma som device_name)
  player_nickname => "PlayerName" (detekterat från CoinPoker UI via OCR/UI Automation)
  player_nickname_confidence => "100" (confidence score 0-100)
  player_email => "player@example.com" (detekterat från login-fönster via UI Automation)
  ip_address => "192.168.1.100" (enhetens IP-adress)
  last_seen => "1732531200" (UNIX timestamp i sekunder)
  threat_level => "35" (bot probability 0-100)
  session_start => "1732530000" (UNIX timestamp när sessionen startade)
  signal_count => "42" (totalt antal detektioner)
  unique_detection_count => "15" (antal unika threat_id)

TTL: 604800 sekunder (7 dagar) - sätts automatiskt vid varje uppdatering

Användning:
- Hashar gör att man kan uppdatera enskilda fält utan att skriva om hela objektet
- HSET används för att uppdatera fält
- HGETALL används för att läsa hela device-info
- Dashboarden läser dessa hashar för att visa spelarinfo

2. Sorterade mängder (Sorted Sets)
-----------------------------------

2a. Device Index (`devices`)
Key: `devices`
Medlemmar: device_id
Poäng: last_seen timestamp (i millisekunder)
Användning: Håller koll på alla enheter sorterade efter senaste aktivitet
Operationer: ZADD för att uppdatera, ZREVRANGE för att få senaste enheter

2b. Top Players (`top_players:bot_probability`)
Key: `top_players:bot_probability`
Medlemmar: device_id
Poäng: threat_level (bot probability 0-100)
Användning: Snabb sortering av spelare efter hotnivå för leaderboards
Operationer: ZADD för att uppdatera, ZREVRANGE 0 19 för top 20

2c. Session Index (`sessions:{device_id}`)
Key: `sessions:{device_id}`
Medlemmar: session timestamps
Poäng: session start timestamp
Användning: Håller koll på alla sessioner för en specifik enhet

3. Batch Records (`batch:{device_id}:{timestamp}`)
----------------------------------------------------
Key: `batch:{device_id}:{timestamp}` (t.ex. `batch:462a6a3a5c173a1ea54e05b355ea1790:1732531200`)

Värde: JSON-sträng med komplett batch report:
{
  "scan_type": "unified",
  "batch_number": 42,
  "bot_probability": 35.5,
  "nickname": "PlayerName",
  "device_id": "462a6a3a5c173a1ea54e05b355ea1790",
  "device_name": "DESKTOP-XYZ",
  "device_ip": "192.168.1.100",
  "timestamp": 1732531200.123,
  "aggregated_threats": [...],
  "summary": {
    "critical": 0,
    "alert": 1,
    "warn": 2,
    "info": 5
  }
}

TTL: 604800 sekunder (7 dagar)

Användning: Historisk data för varje batch som skickas (var 92:e sekund)

4. Batch Indexes (Sorted Sets)
--------------------------------

4a. Hourly Batches (`batches:{device_id}:hourly`)
Key: `batches:{device_id}:hourly`
Medlemmar: batch timestamps
Poäng: timestamp
Användning: Snabb lookup av batches per timme

4b. Daily Batches (`batches:{device_id}:daily`)
Key: `batches:{device_id}:daily`
Medlemmar: batch timestamps
Poäng: timestamp
Användning: Snabb lookup av batches per dag

5. Player Summary (`player_summary:{device_id}`)
-------------------------------------------------
Key: `player_summary:{device_id}`

Värde: JSON-sträng med aggregerad statistik:
{
  "device_id": "462a6a3a5c173a1ea54e05b355ea1790",
  "device_name": "DESKTOP-XYZ",
  "avg_bot_probability": 35.5,
  "avg_score": 20.0,
  "total_reports": 150,
  "total_detections": 500,
  "total_sessions": 10,
  "averages": {
    "programs": 5.2,
    "auto": 3.1,
    "network": 1.5
  },
  "first_seen": 1732000000,
  "last_seen": 1732531200,
  "updated_at": 1732531200
}

Användning: Snabb access till aggregerad data för en spelare utan att behöva räkna om från batches

6. Session Records (`session:{device_id}:{timestamp}`)
-------------------------------------------------------
Key: `session:{device_id}:{timestamp}`

Värde: JSON-sträng med session-info:
{
  "device_id": "...",
  "session_start": 1732530000,
  "session_end": 1732536000,
  "duration": 6000,
  "threat_levels": [10, 15, 20, 25],
  "detections": 42
}

Användning: Historik över individuella sessions

7. Detection Counters (`device:{device_id}:detections:{SEVERITY}`)
-------------------------------------------------------------------
Keys:
- `device:{device_id}:detections:CRITICAL`
- `device:{device_id}:detections:ALERT`
- `device:{device_id}:detections:WARN`

Värde: Antal detektioner av denna severity (integer som sträng)

Användning: Snabb räkning av detektioner per severity-nivå

8. Device Categories (`device:{device_id}:categories`)
-------------------------------------------------------
Key: `device:{device_id}:categories`

Värde: JSON-sträng med kategori-statistik:
{
  "programs": 5,
  "auto": 3,
  "network": 2,
  "behaviour": 1,
  "vm": 0
}

Användning: Snabb översikt över vilka kategorier som detekterats

9. Device Threat (`device:{device_id}:threat`)
-----------------------------------------------
Key: `device:{device_id}:threat`

Värde: Senaste threat_level (bot probability) som sträng (t.ex. "35")

Användning: Snabb lookup av aktuell hotnivå utan att läsa hela device hash

10. Time-based Aggregates
--------------------------

10a. Day Stats (`day:{device_id}:{YYYY-MM-DD}`)
Key: `day:{device_id}:2024-11-25`

Värde: Hash med daglig statistik

10b. Hour Stats (`hour:{device_id}:{YYYY-MM-DDTHH}`)
Key: `hour:{device_id}:2024-11-25T14`

Värde: Hash med timvis statistik

11. Pub/Sub Channels
--------------------

11a. Device Updates (`updates:{device_id}`)
Channel: `updates:{device_id}`

Meddelanden publiceras när en enhets data uppdateras (t.ex. ny batch, threat level ändras)

11b. Global Updates (`updates:all`)
Channel: `updates:all`

Meddelanden publiceras för globala events (t.ex. ny enhet online)

Användning: Realtidsuppdateringar till dashboarden via Server-Sent Events (SSE)

12. Command Queue (Bidirectional Communication)
------------------------------------------------

12a. Command Queue (`device:{device_id}:command_queue`)
Key: `device:{device_id}:command_queue`

Värde: List (LPUSH/RPOP) med kommando-ID:n

12b. Command Details (`device:{device_id}:commands:{command_id}`)
Key: `device:{device_id}:commands:{command_id}`

Värde: JSON med kommando-info:
{
  "command": "kill_coinpoker" | "take_snapshot",
  "timestamp": 1732531200,
  "status": "pending" | "completed" | "failed"
}

12c. Command Result (`device:{device_id}:command_result:{command_id}`)
Key: `device:{device_id}:command_result:{command_id}`

Värde: JSON med resultat från kommandot

Användning: Dashboarden kan skicka kommandon till scannern via Redis

Player Identification
======================

Nickname Detection:
- Detekteras via OCR (Tesseract) eller UI Automation (pywinauto)
- Lagras i `device:{device_id}` → `player_nickname`
- Confidence score lagras i `player_nickname_confidence`
- Skickas som "Player Name Detected" system signal

Email Detection:
- Detekteras från CoinPoker login-fönster via UI Automation (pywinauto)
- Körs en gång per session när login-fönster detekteras
- Lagras i `device:{device_id}` → `player_email`
- Skickas som "Player Email Detected" system signal

Både nickname och email visas i dashboarden på player profile-sidan.

Kodsynk mellan scanner och dashboard
=====================================
- Python-scannern använder `core/redis_schema.py` för alla nycklar samt `core/device_identity.py` (läser `config/redis_identity.json`) för att bestämma nickname/device-namn och spara IP-adress.
- Next.js-dashboarden använder motsvarande `lib/redis/schema.ts` och `lib/device/identity.ts`, vilket gör att både HTTP-flödet och direkta Redis-skrivningar producerar identiska strukturer.

Prestanda och skalning
=======================
- Redis är en in-memory databas som använder en single-threaded event-loop och kan hantera >100 000 förfrågningar per sekund
- Med 4 000 spelare finns gott om kapacitet
- Sorted sets har O(log N) komplexitet för operationer
- Hashar gör att man kan uppdatera enskilda fält utan att skriva om hela objektet
- TTL på 7 dagar säkerställer att inaktiva enheter rensas automatiskt

TTL Policy
-----------
- Standard TTL: 604800 sekunder (7 dagar)
- Sätts automatiskt vid varje uppdatering av device hash
- Inaktiva enheter rensas automatiskt efter 7 dagar utan aktivitet

Exempelkod (Python)
===================
Följande Python-exempel visar hur man kan uppdatera en spelares data:

```python
import redis
import time
from core.redis_schema import redis_keys

# Anslut till Redis
r = redis.Redis(host='localhost', port=6379, db=0)

def update_device(device_id: str, threat_level: float, player_nickname: str = None, player_email: str = None):
    """Uppdatera enhetens data i Redis."""
    device_key = redis_keys.device_hash(device_id)
    now_seconds = int(time.time())
    
    # Uppdatera device hash
    fields = {
        "device_id": device_id,
        "last_seen": str(now_seconds),
        "threat_level": str(int(threat_level)),
    }
    
    if player_nickname:
        fields["player_nickname"] = player_nickname
    
    if player_email:
        fields["player_email"] = player_email
    
    r.hset(device_key, mapping=fields)
    r.expire(device_key, 604800)  # 7 dagar
    
    # Uppdatera sorted sets
    r.zadd(redis_keys.device_index(), {device_id: now_seconds * 1000})
    r.zadd(redis_keys.top_players(), {device_id: threat_level})
    
    # Publicera uppdatering
    r.publish(redis_keys.device_updates_channel(device_id), f"{{'id': '{device_id}', 'threat': {threat_level}}}")

# Exempelanrop
update_device('462a6a3a5c173a1ea54e05b355ea1790', 75.0, player_nickname="PlayerName", player_email="player@example.com")
```

Sammanfattning
==============
För att hantera omkring 4 000 spelare i en realtidsmiljö använder systemet:
- Hashar (`device:{device_id}`) för strukturerad data per spelare
- Sorted sets (`devices`, `top_players:bot_probability`) för effektiva rangeringar
- Batch records (`batch:{device_id}:{timestamp}`) för historisk data
- Player summaries (`player_summary:{device_id}`) för aggregerad statistik
- Pub/Sub channels (`updates:{device_id}`, `updates:all`) för realtidsuppdateringar
- TTL på 7 dagar för automatisk rensning av inaktiva enheter

Redis är extremt snabb tack vare sitt in-memory-och single-threaded-upplägg och sorted set-operationerna har logaritmisk tidskomplexitet, vilket gör denna lösning skalbar för 4 000 spelare och långt därutöver.
